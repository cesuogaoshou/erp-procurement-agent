# Decisions

## 2026-10-10: Phase 1 Uses Deterministic Backend Before LLM

Decision: implement inventory, baseline forecast, shortage calculation, supplier recommendation, and evaluation before adding LLM orchestration.

Rationale: the outline requires backend-owned numerical and business rules, and deterministic services are necessary for testing and for later Function Calling tools.

Alternatives considered: start with Agent Loop first. Rejected because it would risk a scripted demo without verified business foundations.

Revisit when: deterministic flow can create and evaluate purchase recommendations without LLM.

## 2026-10-10: Phase 1 Excludes In-Transit Supply

Decision: shortage calculation currently uses `on_hand - reserved` and sets confirmed inbound supply to zero.

Rationale: the initial data model does not yet include confirmed inbound purchase order snapshots, and the outline allows simplification when consistently documented.

Alternatives considered: add inbound order snapshots immediately. Deferred to keep the first slice focused on inventory, shortage, recommendation, and evaluation foundation.

Revisit when: purchase order persistence and approval are implemented.

## 2026-10-10: Recommendation Labels Use Scenario Thresholds

Decision: the frozen supplier recommendation cases use `scenario_thresholds_v1` labels based on scenario-specific raw thresholds such as rush lead time, quality, complaint rate, and budget.

Rationale: the course requires labels not generated by the same tested weighted scoring formula. Threshold labels are simple, explainable, and independent from the composite normalization/weighting implementation.

Alternatives considered: use the composite score itself to label acceptable suppliers. Rejected because it would leak the tested formula into the evaluation target.

Revisit when: manual labels or post-decision simulated fulfillment outcomes are available.

## 2026-10-10: Approval Uses Auth Context And Backend Revalidation

Decision: approval authorization uses the resolved backend `AuthContext` only. The API may accept body actor fields for compatibility tests, but services ignore them for identity and role decisions.

Rationale: user/role claims in request bodies can be forged. The project boundary requires backend-owned permissions, calculations, constraints, transactions, and idempotency.

Alternatives considered: trust `actor_user_id` or `actor_role` from approval request bodies. Rejected because it would allow privilege escalation.

Revisit when: production authentication middleware or a real identity provider is introduced.

## 2026-10-10: Demo Auth Uses Server-Signed Tokens By Default

Decision: approval API authentication now defaults to a server-signed bearer token issued by preset demo accounts. Direct `X-User-Id` and `X-User-Role` headers are accepted only when `allow_header_auth=True` is explicitly enabled for tests.

Rationale: client-controlled headers are forgeable and cannot be treated as authentication. The course demo needs a minimal but defensible server-side identity source without building full user management.

Alternatives considered: continue trusting headers in normal mode. Rejected because forged role headers could cross the approval boundary.

Revisit when: a production identity provider or session middleware is introduced.

## 2026-10-10: Approval Generates Formal Order Number On Approval

Decision: approving a pending order changes status to `approved` and assigns a unique `formal_order_number` such as `PO-000001`.

Rationale: the course scope needs a deterministic formal order transition without integrating real supplier execution, payment, or email.

Alternatives considered: create a separate formal order table immediately. Deferred to avoid expanding beyond the current procurement decision loop.

Revisit when: separate lifecycle tracking for issued, received, canceled, or closed orders is required.

## 2026-10-10: Agent Tools Exclude Approval Actions

Decision: the model tool surface includes read-only procurement tools and `create_purchase_draft` only. Approval and rejection remain direct authenticated backend/API actions and are not registered as model tools.

Rationale: LLM responsibilities are limited to intent understanding and tool orchestration. Approval is a permissioned business control and must not be delegated to model output.

Alternatives considered: expose approval as an Agent tool with role checks. Rejected because it expands the model's action surface beyond the deterministic procurement loop.

Revisit when: a human-in-the-loop approval UI or audited workflow engine is available, while keeping final approval outside model control.

## 2026-10-10: Agent Drafts Require Server Forecast Evidence

Decision: Agent-created purchase drafts must reference server-generated forecast evidence, and requested quantities cannot exceed the server-calculated shortage for the referenced material forecast.

Rationale: model-generated quantities are untrusted. The backend owns numerical forecasting, shortage calculation, and draft validation.

Alternatives considered: allow the model to pass any quantity when recommendation evidence exists. Rejected because recommendation evidence does not prove a demand shortage.

Revisit when: shortage calculation includes confirmed inbound supply or multiple forecast models with confidence bands.

## 2026-10-10: Forecast Comparison Reports Raw Results And Failures

Decision: moving-average and Prophet comparison uses identical windows and reports raw demand/shortage errors, zero-shortage coverage, runtime, and failures. Prophet failure is reported when the optional dependency is unavailable.

Rationale: the course requires comparison evidence, not a preselected winner. Optional model failures must be visible rather than hidden.

Alternatives considered: skip Prophet until installed or emulate Prophet with another model. Rejected because that would obscure acceptance status.

Revisit when: forecast model scope changes or additional models are compared on the same frozen windows.

## 2026-10-10: Persist Agent State And Trace Before Real LLM Acceptance

Decision: Agent runs and tool traces are persisted before real LLM calls are accepted. This started as durable state management before real LangGraph package execution was available.

Rationale: restart visibility and auditability are required before expanding model autonomy.

Alternatives considered: keep Agent state only in memory until real LLM integration. Rejected because in-memory state would not satisfy restart query requirements.

Revisit when: cross-process LangGraph checkpoint restoration becomes required.

## 2026-10-11: LangGraph Execution Is Real, Recovery Is Database-Owned

Decision: use a real LangGraph `StateGraph` wrapper for procurement Agent execution, while keeping durable recovery in project tables (`agent_runs`, `tool_traces`, and purchase order state) instead of claiming a durable LangGraph checkpoint backend.

Rationale: the installed LangGraph package validates actual graph execution, but the available local dependency set does not include a cross-process sqlite checkpoint package. The project already persists the audit-relevant run, trace, draft, pending approval, and formal order state in SQL.

Alternatives considered: call the existing Agent loop "LangGraph-style" or require LangGraph checkpoint persistence before accepting any LangGraph work. Rejected because the first is not real LangGraph execution, and the second is beyond the current backend acceptance need.

Revisit when: the demo needs step-level graph resume after process death rather than restart queryability and approval recovery from SQL state.

## 2026-10-11: MOQ And Package Multiples Are Backend Rules

Decision: draft creation rounds requested quantities up to satisfy both supplier MOQ and package multiple. Approval revalidates package multiple, quote, capacity, and supplier/material relationship before generating a formal order.

Rationale: model output and client requests cannot own procurement quantities. Keeping rounding and revalidation in backend services preserves deterministic auditability and idempotent retry behavior.

Alternatives considered: reject quantities below MOQ or let the model adjust to packaging. Rejected because it would either fail reasonable procurement requests or trust non-authoritative model arithmetic.

Revisit when: packaging rules need material-specific UOM conversions or split-line supplier allocation.

## 2026-10-11: Real Provider Requests Must Send Tool Schema

Decision: OpenAI-compatible provider calls must include the backend-defined Agent `tools` schema with `tool_choice: auto`. The schema is generated from `build_agent_tools()`, so approval and rejection remain excluded from the model tool surface.

Rationale: setting `tool_choice` without sending tool definitions cannot validate real Function Calling. The model may only orchestrate allowed procurement tools; backend services still own SQL access, calculations, permissions, approvals, transactions, idempotency, and audit logs.

Alternatives considered: rely on mock-provider tests or prompt-only tool descriptions. Rejected because mock providers do not prove real API tool selection, and prompt-only descriptions are not Function Calling.

Revisit when: the provider protocol needs multi-tool-call response handling or provider-specific schema variants.

## 2026-10-11: MySQL Integration Test Is Explicitly Opt In

Decision: MySQL concurrency, rollback, and persistence validation lives in `backend/tests/test_mysql_integration.py` and runs only when `RUN_MYSQL_INTEGRATION=1`.

Rationale: the project must not confuse SQLite unit tests with MySQL row-lock behavior, but the default test suite should remain runnable offline. The opt-in test records its report to `reports/generated/mysql_integration.json` when `MYSQL_INTEGRATION_REPORT_PATH` is set.

Alternatives considered: always run the MySQL test inside `python -m pytest backend/tests -q`. Rejected because default local tests should not require live credentials or mutate a shared integration database.

Revisit when: a dedicated disposable MySQL test database or containerized CI database is always available.

## 2026-10-11: Provider Accepts OpenAI-Compatible Base Roots

Decision: `OpenAIFunctionCallingProvider` accepts a provider base root such as `https://api.deepseek.com` and normalizes it to `/chat/completions`. Fully specified `/chat/completions` URLs remain valid.

Rationale: user-facing provider configuration normally uses a base URL, while the internal HTTP call needs the concrete chat completions endpoint. Normalizing once in the provider avoids brittle environment setup.

Alternatives considered: require `OPENAI_BASE_URL` to include `/chat/completions`. Rejected because it is easy to misconfigure and differs from common OpenAI-compatible documentation.

Revisit when: adding providers that do not expose an OpenAI-compatible chat completions path.

## 2026-10-11: Prophet Requires Explicit Minimum Training History

Decision: Prophet comparison now uses `ProphetForecastConfig(name="prophet_weekly_yearly_min365")` and reports windows with fewer than 365 training samples as `insufficient_history` failures instead of fitting and counting unstable forecasts.

Rationale: diagnostics showed no train/holdout ordering bug, no missing daily rows, correct 30-day aggregation, correct negative forecast clipping, and the required shortage formula. The major error source was early 45-75 day training windows where yearly+weekly Prophet produced extreme 30-day totals. After enough history is available, the same config is materially more stable. Reporting short-history failures is more honest than counting under-identified forecasts as successful Prophet predictions.

Alternatives considered: disable yearly seasonality, use trend-only Prophet, shorten the training window, or regenerate easier simulated data. Validation-window comparison favored the existing yearly+weekly configuration once enough history existed, and regenerating data would violate the frozen-data rule.

Revisit when: additional true historical demand is available, a separate final test period is created before being inspected, or the course accepts a fallback policy that routes insufficient-history materials to the moving-average baseline while still reporting Prophet coverage separately.

## 2026-10-11: Forecast Reports Separate Pure Model Coverage From Hybrid Coverage

Decision: forecast comparison now reports four distinct scopes: full 160-window moving average, long-history Prophet on its 50 successful windows plus 110 explicit failures, moving average recalculated on those same 50 Prophet-success windows, dynamic-seasonality Prophet with weekly-only short-history behavior and yearly+weekly long-history behavior, and a separate hybrid strategy that falls back to moving average for dynamic Prophet failures.

Rationale: Prophet failure windows must remain visible in overall reporting, and a fallback policy is an operational strategy rather than a pure Prophet metric. The 365-day yearly-seasonality threshold is a project engineering guard for this simulated dataset and should not be described as a universal Prophet requirement.

Alternatives considered: present only successful Prophet metrics, hide insufficient-history windows, or call the hybrid output Prophet. Rejected because each would overstate model coverage or blur the distinction between model accuracy and operational fallback coverage.

Revisit when: a new untouched final test range exists, additional historical demand/inventory data is available, or a course rubric explicitly asks for a different fallback policy.

## 2026-10-11: Shortage Backtests Are Fixed-Inventory Scenario Tests

Decision: demand backtests remain rolling historical demand comparisons, but shortage metrics are documented as a fixed-inventory scenario using the static 2026-10-10 inventory snapshot.

Rationale: the current seed/export data has one inventory row per material and no dated inventory movement or historical stock snapshot table, so true historical shortage reconstruction is not available.

Alternatives considered: infer historical inventory from current stock and demand. Rejected because that would fabricate inventory history and violate the project rule against invented experiment evidence.

Revisit when: historical inventory snapshots, stock movements, receipts, reservations, and in-transit supply are modeled and seeded.

## 2026-10-11: Freeze Forecast Strategy For Course Delivery

Decision: freeze the current forecast strategy as `forecast_strategy_v1_20261011`. The actual service strategy is `hybrid_dynamic_prophet_or_moving_average_30d`: dynamic Prophet is the main prediction path, and short-history or Prophet execution failures fall back to `moving_average_30d`.

Rationale: exploratory diagnostics already consumed the current validation/test windows, and further tuning would risk turning the report into post-hoc optimization. Freezing the strategy lets the backend, Agent tool, reports, and course package describe one consistent version.

Alternatives considered: continue tuning Prophet thresholds, regenerate easier data, or relabel frozen cases. Rejected because the user explicitly froze prediction work and because changing frozen evidence would violate the project acceptance rules.

Revisit when: a new untouched final split is created before inspection, or real historical demand/inventory data becomes available.

## 2026-10-11: Forecast Evidence Is Persisted Without A Schema Migration

Decision: forecast tool output persists full forecast evidence in `tool_traces.output_json`; Agent-created purchase drafts persist resolved forecast evidence references and payloads in the existing `purchase_orders.evidence_refs_json` field. Direct API/manual draft calls that only provide refs keep the legacy list format.

Rationale: the current schema already has durable trace and evidence JSON fields. Reusing them records model name, selected model, config version, training range, fallback reason, and evidence ref without expanding schema late in the delivery cycle.

Alternatives considered: add new forecast evidence tables or purchase order columns. Deferred because the requested behavior can be satisfied by existing JSON persistence and avoids unnecessary migration risk.

Revisit when: forecast evidence needs first-class querying, retention rules, or cross-order analytics.

## 2026-10-12: Frontend Is A Thin Demo Client

Decision: the Vue frontend is a minimal course/demo client that calls backend APIs for Agent execution, forecasting, supplier scoring, draft creation, submission, approval, and order queries. It does not hard-code business outcomes, calculate scores, approve orders locally, or embed credentials.

Rationale: project boundaries require backend-owned SQL access, calculations, permissions, approvals, transactions, idempotency, and audit behavior. The frontend should demonstrate and inspect the real procurement loop without expanding into a full ERP or production identity system.

Alternatives considered: implement richer frontend-side orchestration or mock the Agent result for a smoother demo. Rejected because that would blur the backend acceptance boundary and risk fabricated workflow evidence.

Revisit when: production identity, richer UX, or a broader ERP module scope is explicitly added.

## 2026-10-12: Runtime Configuration Is Loaded From Root `.env`

Decision: backend app startup, Alembic, and real-model acceptance load the project-root `.env` file while preserving already-set process environment variables as higher priority.

Rationale: README-style new processes need consistent `DATABASE_URL`, `OPENAI_BASE_URL`, and model configuration without manually re-exporting variables into every shell. This directly fixes the earlier drift where the browser server process lacked `OPENAI_BASE_URL`.

Alternatives considered: keep manual shell exports. Rejected because it is easy to start a child process without the same provider configuration.

Revisit when: the project adopts a full typed settings object or deployment-specific secret manager.

## 2026-10-12: Real Provider Base URL Is Explicit

Decision: real provider construction requires `OPENAI_BASE_URL`; missing base URL returns `OPENAI_BASE_URL_missing` and does not print secrets.

Rationale: model names and provider roots are coupled for OpenAI-compatible services. Silently defaulting to another provider root creates unclear HTTP failures.

Alternatives considered: default to OpenAI or DeepSeek. Rejected because defaults can route to the wrong provider.

Revisit when: provider-specific profiles are added with explicit names and validation.

## 2026-10-12: Demo Reset Requires A Demo Database

Decision: demo-data reset requires an explicit `--database-url` whose database or file name contains `demo`.

Rationale: the reset command clears all project tables. It must not implicitly clear a database inherited from ambient `DATABASE_URL`.

Alternatives considered: keep `DATABASE_URL` as the default reset target. Rejected as too risky for repeatable course rehearsals.

Revisit when: a safer fixture namespace or tenant-scoped reset mechanism exists.

## 2026-10-12: Draft Creation Requires Shared Server Evidence Validation

Decision: Agent tool draft creation and direct `/purchase-drafts` creation both call the same purchase draft service validation. Valid draft evidence must include a current server forecast ref for the material and recommendation evidence for the supplier/material/rounded order quantity. Requested quantity cannot exceed server shortage, while MOQ/package-multiple rounding remains allowed when backed by recommendation evidence for the rounded quantity.

Rationale: model and client-supplied evidence refs are untrusted. A placeholder evidence string is not enough to prove material, forecast, quantity, supplier, quote, or recommendation basis.

Alternatives considered: keep stricter checks only in `agent_tools.py`, or reject all MOQ/package rounding above the forecast shortage. Rejected because direct API callers would bypass business evidence checks, and rejecting justified packaging would contradict the procurement business rule already accepted by approval validation.

Revisit when: evidence refs become first-class database records or draft lines support split suppliers and partial shortage coverage.

## 2026-10-12: Minimal Object-Level Read Scoping Uses Existing Persistence

Decision: add minimal read authorization using `AgentRun.state_json` for run ownership and `AuditLog(action="created_draft")` for Agent-created order ownership. Buyers can read their own runs, traces, and orders; approvers can read approval-needed/processed orders and associated traces.

Rationale: the course remediation needs object-level read protection against cross-user listing and guessed IDs, but not a full ERP permission platform or schema migration.

Alternatives considered: add full owner columns and migrations, or leave read APIs login-only and document the limitation. The first was broader than the requested minimal整改, and the second left a concrete acceptance gap.

Revisit when: production identity, teams, departments, delegated approvals, or tenant-level isolation are introduced.

## 2026-10-28: Draft HTTP ownership uses the existing creator audit

Decision: authenticate the direct draft HTTP boundary as buyer, write order and `created_draft` audit in the same transaction, and use the first creator audit (timestamp then ID) for read/replay/submit ownership. A replay never adds another creation audit. Agent HTTP replay must preserve that creator and cannot relabel a different buyer's order. Unowned historical orders are not claimable through direct draft replay/submission. Existing trusted internal service entrypoints retain their contract.

Rationale: closes the concrete P1 without schema migration or fabricated owner backfill. Uses the existing persisted read authorization source and keeps transaction failure safe. Frontend role disabling is a convenience; HTTP checks remain authoritative.

Alternatives: add owner columns/migrate all historical orders, or merely gate draft creation by role. The former expands this course repair; the latter permits cross-buyer idempotency/submit access and leaves direct drafts unqueryable by their creators.

Verification: signed-token regressions include owner/non-owner draft/pending replay, same-transaction audit rollback, and Agent duplicate/cross-buyer replay. Live HTTP and browser/MySQL evidence are indexed by docs/REMEDIATION_ACCEPTANCE_20261028.md.

Review follow-up: recheck the service-returned order creator before adding a creator audit, because a key may be committed between the route's first query and the service query. Deterministic interleaving regressions cover same-owner audit deduplication and different-owner 403; both failed before the post-service check and passed after it. The Agent internal creation/ownership transaction split remains unchanged.

Revisit when: moving beyond signed demo identities, adding ownership transfers/tenants, or requiring atomic ownership in every internal Agent transaction as a production contract.

## 2026-10-29: Procurement safety context and transactions

- Structured prompt + total_budget is the minimal confirmed procurement demand context. Persist budget on run/order; model write parameters cannot carry or replace it. Unknown historical values stay NULL; approval of an unknown-budget draft is blocked, rejection remains possible. No new full demand-management module.
- Aggregate requested quantities by material before shortage comparison; apply MOQ/package ceiling once; persisted actual quantity requires capacity and recommendation coverage. Store pre-rounding demand to keep legitimate MOQ behavior during approval.
- Recover only the order-idempotency unique index under SAVEPOINT rollback. Under MySQL REPEATABLE READ, winner order, items and creator use current reads; normal snapshot reads after collision are insufficient. Keep atomic order/creation audit. Canonical request identity preserves Decimal equality, rejects changed content and malformed evidence.
- Commit run identity before tools; isolate each business tool and roll back before logging errors. Tool runtime models generate provider schemas, with local validation always mandatory. Keep bounded LLM orchestration (8 calls, 180s plus request timeout), reuse per-material latest evidence and forecast-inventory output.

## 2026-10-29 业务反馈与最小确认流程

使用capture_request提取需求，并由后端目录解析、原文及预算栏核对、后续工具条件守卫裁决。未明确数量/交期/预算、歧义、未知物料和隐式加购必须暂停；用户补齐原需求后新运行，不把模型猜测当同意。

中文主结论与下一步由后端事实构造，模型文字保存为辅助排查内容。使用现有AgentRun.state_json持久化business_message/next_action/model_response，无新增迁移，历史未知字段明确显示未知。模型安全停单时后端仍用已比较供应商方案总价计算/解释整单预算不足。

选择现有表和工具编排最小扩展，避免仅展示模型回复造成事实冲突，也避免扩大成聊天平台；订单计算/证据/数量汇总/预算/权限/事务/审批/幂等继续由原服务控制。MOQ或包装导致多买一律要求明确新数量，不接受模型的allow-extra推断。


## 2026-10-29 原文绑定与明确确认
- 模型capture_request只是候选；服务端独立绑定原文物料全集、逐项数量、单位、禁写意图、交期与当前整单预算。不可靠关联必须完整清单确认，明确矛盾直接拒绝。
- 有效需求持久化并以source_run_id绑定原始AgentRun；推荐/建草稿复核，批准还独立反查关联AgentRun，不能删除订单锚点降级为原文自比。历史订单不回填新锚点。
- 人工确认专用buyer接口，不暴露为模型工具；绑定原文/预算/记录/所属人，一次消费。界面编辑后旧确认禁用。不会替代后续人工订单审批。
- 金额完整词元解析和就近预算语境，不截取非法分组的局部数字；交付时间单位规范化，两周固定14天，歧义追问。未改预测参数、冻结数据、事务/幂等/权限机制。


## 2026-10-29 最终补强
- 原文显式数量/交期也约束只读推荐，不把缺失的分析条件用模型猜测补成确认；条件禁写只有明确失败条件才可作条件语义，普通“如果方案合适”不能解禁。
- Agent草稿幂等键由服务端run_id确定，模型键不决定跨运行订单身份；同运行重复工具执行幂等，直接建单API/服务协议不变，不声称已支持跨新运行HTTP请求去重。
- 审批从最初创建运行发现来源，不让后续幂等关联追溯改变历史订单锚点。最终验证203后端/6MySQL/26真实接口与最终浏览器闭环；以FINAL_REACCEPTANCE报告为准。
