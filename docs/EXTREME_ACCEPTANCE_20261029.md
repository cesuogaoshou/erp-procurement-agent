## 发现的问题

### P1：重复物料行绕过合计缺口和容量

`G1_duplicate_material_rows_aggregate_limits` 请求同物料4行、每行120件，分别引用合法的120件推荐证据。当前缺口406.11、供应商容量300；合计480件仍 HTTP 200 创建 **#63，3888.00元**。

根因：`purchase_drafts.py` 逐行验证，未按物料聚合。实际 MySQL 审批服务探针也接受该订单，但事务已回滚，最终通过正常接口驳回隔离。

建议：统一重复物料行，验证合计申请量与缺口、合计取整量与容量，审批时复验。保留现有 MOQ 合法取整规则，不能简单禁止一切取整超出原申请量。

### P1：整单共享预算缺少表达和硬校验

`G2_multi_material_total_budget` 为物料1/2各120件，分别取得预算1000的推荐证据。单行972/984均低于1000，但合计 **1956.00元**仍创建 **#64**；审批回滚探针也未拒绝。最终 #64 已驳回隔离。

草稿 API 没有整单预算字段，仅推荐引用中有各自预算。因此这是“无法表达并强制执行共享预算”的能力缺口，不是某个已有整单预算字段被绕过。

真实模型诊断复试 **#87** 正确将第二种物料剩余预算设为 **28元**，无候选、无草稿；该次模型遵守要求不能替代后端硬约束。建议将经确认的采购需求与整单预算绑定，在创建和审批时计算总额校验。

### P1：只读 Agent 分析返回500并丢失运行轨迹

接口和页面均复现 **500 Internal Server Error**。日志为 `agent_loop.py::_latest_shortage_is_zero()` 的 `KeyError: 'shortage_quantity'`：证据注册表最后一项是推荐结果，结束逻辑却当作预测结果读取缺口。

没有新增订单，但异常发生在结束状态提交之前，相关运行/轨迹未持久化，页面显示暂无 Trace。建议按预测引用类型读取预测，并对未预期异常受控返回、保留失败执行记录。

### P2：同键并发创建返回未处理的500

`C5_simultaneous_same_key_creation` 两请求同时创建：一次200、一次500，数据库仅有 **#60及一条创建审计**。日志为唯一键 `purchase_orders.idempotency_key` 的 MySQL1062/SQLAlchemy IntegrityError。

建议捕获特定幂等唯一键竞争，rollback后重查并校验归属，安全复用或返回明确冲突；不要吞掉任意数据库错误。数据库阻止重复不等于接口已正确处理竞争。

### P2：内部工具与 HTTP Schema 范围不一致

HTTP 对181天预测、负数数量返回422；直接调用真实 Agent 分发器时：181天预测正常返回缺口2717.07，数量-120正常返回空推荐；NaN在运算中触发Decimal InvalidOperation，而非统一参数错误。

这些是只读事务回滚的工具探针，不是自然语言执行。建议每个工具统一运行时参数模型，检查类型、范围、有限数值、长度和未知字段，再执行现有业务校验。

### P2：普通多物料任务耗尽6次调用

普通共享预算请求 **Run #85** 重复查库存/预测，HTTP409 `max_tool_calls_exceeded`，无草稿。明确“预测包含库存、不再单查库存”的诊断复试 **#87** 用4次调用识别剩余28元，正确停止。

原始失败和复试通过都保留；首次结果不能解释为已正确判断超预算。建议保留限步保护，减少重复调用并明确多物料能力边界，不能只无限加大上限。
